### 1.1 The root cause, verified

- **Backend container** (`yadgar-backend`, owns SurrealDB + MariaDB): `Dockerfile.backend:23`
  installs `curl mariadb-server` — **no git**. `podman inspect` shows three mounts
  (`config.yaml`, `~/.cache/huggingface`, `~/.local/share/yadgar → /data`). **No host project dirs.**
- **Core container** (`yadgar`): `Dockerfile:7` installs `curl` — **no git**. Mounts `.:/app` and
  the data dir. `docker-compose.yml:107` points it at the backend over HTTP, so core never opens
  the DB (ADR-0078/0200). **No host project dirs.**
- `yadgar/core/identity.py:219-240` — `_origin_remote` catches `FileNotFoundError` (the missing
  `git` binary) and returns `""`. Nothing escapes.
- `yadgar/core/identity.py:202-206` — `_local_fallback` is `os.path.basename` on a **string**. It
  does not stat. It **cannot fail**.

So inside either container `derive_project_id("/home/max/git/yadgar")` returns
**`local/yadgar`** — never `m-agahi/yadgar` — silently, every time. That single fact produces
findings #1, #6, #7, #8, #9, #10, #11 and #12.

ADR-0227 settles it: **core and backend derive nothing; the sole minting point is a host-side
script at SessionStart; there are no fallbacks; a missing value fails loud.**

### 1.3 Three decisions the task statement left implicit — decided here

**T1 — the transport.** There is no channel from the SessionStart hook to an MCP tool call.
Verified: `yadgar/core/hooks/session-start-context.py` is **stdout-only** (it prints markdown
into the agent's context and nothing else), and the MCP server is a **shared streamable-HTTP
daemon** registered by URL (`mcp_register.py:_SERIALIZERS`), not a per-session stdio process —
so there is no per-session env var to set, and MCP tool calls carry no `session_id`.

> **Decision: `project` is an explicit caller parameter, and the hook's job is to mint the value
> and emit it into the agent's context.** This is the plain reading of ADR-0227 ("thereafter
> travels as an explicit caller parameter on every call that needs it"). It needs no new
> transport and no hidden daemon state, and fail-loud is what enforces it.

Rejected alternative: a **daemon-side session registry** (hook POSTs the minted id; tools default
to it). Rejected because MCP calls carry no session key, so the daemon would key on *most recent
hook call* — last-write-wins across two concurrent sessions in different repos. That is inference,
which ADR-0227 forbids in terms ("never defaulted, never inferred, never silently substituted").
Adopting it would require an **amending ADR**; it is not a plan-level choice.

**T2 — what "blocking backfill" means mechanically.** ADR-0227 says the in-migration backfill
cannot stand (the container may not derive). The user says the backfill is blocking in this PR.
These reconcile exactly one way:

> The backfill **code ships in this PR** as an operator-invoked admin op that takes a
> **host-resolved manifest** and defaults to `dry_run=True`. Migration 031 keeps only its
> `DEFINE FIELD` / `DEFINE INDEX` phases. **Execution** of the backfill is a gated step in the
> rehearsal (§8) and the runbook, and it is a **release blocker** — the read path flips onto
> `project_id` in this same PR (C7), so deploying C7 against an un-backfilled corpus makes
> recall return nothing.

**T3 — the ADR-0225 carve-out list.** ADR-0225's own text keeps `YADGAR_DIRECTORY_ENFORCEMENT`
"until the registry check (`_ensure_project_exists`) is actually wired". Findings #3/#4 wire it
**inside this PR** (C6). The knob's stated end condition is therefore met here, and **the knob
dies here** — consistent with ADR-0225, not a contradiction of it. Surviving carve-outs:

1. the SessionStart / CLI mint's **path input** (owner/repo can only come from a real tree);
2. `directory_context` as a **stored column**, dropped in the NEXT PR;
3. **genuine filesystem paths** — config/data/log/snapshot dirs, `_list_worktrees(directory)`
   (`_shared/restoration/transcript_parse.py:254`), staleness hashing on a real file path;
4. **historical mentions** in ADRs and archived plans, which are correct as written.

### 1.4 The scoping model — ownership and reach are different facts

**Settled with the user 2026-08-10, and it replaces "`global` as a project_id".**

> **`project_id` is ownership / provenance. It is ALWAYS a real registered project — never a
> sentinel, never `"global"`.** Cross-project *reach* is a separate, orthogonal fact: a **`global`
> tag** on the row.

**Why.** Today a memory that applies everywhere must **surrender its origin** to become visible
everywhere. A gotcha found in `tf-toolkit` that applies to every terraform repo is still *from*
`tf-toolkit` — and `directory_context="global"` destroys that provenance permanently and
irreversibly. Ownership and reach are different facts and get different fields.

**The retrieval predicate becomes:**

```
project_id = :current  OR  'global' IN tags
```

**Three consequences that are work, not wiring:**

1. **`recall(tags=[…])` is wiki-only and inert for memories.** `recall_pipeline.py:439` constructs
   `WikiProvider(_st._wiki, tags=tags, exclude_tags=wiki_exclude)`; the `MemoryProvider` at `:424`
   **never receives tags**. So `'global' IN tags` as a *memory* predicate must be **BUILT**, not
   wired. (C7.)
2. **`storage_scope="global"` changes meaning rather than disappearing.** `policy.py:193,230`
   declare it for the agent-library and TOC page types, and `_shared/wiki/store.py:717-722` acts
   on it by **overriding the caller-supplied `directory_context` to `"global"` at write time**.
   Under the new model that write becomes *"stamp the true `project_id` **and** add the `global`
   tag"*. The field survives; its effect moves from the ownership column to the reach tag.
3. **Array containment is on the hot path.** `'global' IN tags` runs per query on both stores.
   **Measure, do not assume** — see the exit criterion in §9 and V10 in §11.

**The corpus is not clean, and the numbers are bigger than "~80 orphans".** Measured live via
`db_inspect` 2026-08-10:

| sentinel | table | rows | disposition |
|---|---|---|---|
| `directory_context = "global"` | `wiki_page` | **80** | → `local/aws-work` + `global` tag (§1.5 decision G) |
| `directory_context = "global"` | `memory` | **349** | same class — **not covered by the "~80 orphans" framing** |
| `directory_context = "system"` | `memory` | **604** | **a SECOND sentinel nobody named.** `is_directory_eligible` excludes `'system'` explicitly (v5.65, `providers/wiki.py:71`). Sampled rows are consolidation output tagged `derived`/`auto-generated`, with source paths pointing mostly at `aws-work`. Under "always a real project" these need a real owner too — **decided in C6**, not assumed. |
| free-text prose in `directory_context` | `memory` | **18 distinct values** | e.g. `"Hard rule from Max set 2026-05-07 — must survive compaction"`, `"debugging opsecrets nixos-quinyx"`. This is `memorize(context=)`'s docstring being violated **in the live corpus** — the C10(f) defect, with receipts. |

**Total sentinel rows: 1,033 of 5,349 — ~19% of the corpus** (80 + 349 + 604). **The free-text-prose
class is NOT in that sum** — it is 18 *distinct values*, not 18 rows, listed alongside because it is
the same review problem, not the same arithmetic. The backfill manifest (C6) must enumerate all
four classes, not just the wiki `global` 80.

**Distinct `directory_context` values: 31 on `wiki_page`, 128 on `memory`.** Many are *subdirectories
of one repo* — `qwfm` alone appears under 6 distinct values, `infrastructure-services` under 8.
Those collapse onto one `project_id`, which is exactly the collision C10(e) decides for
`code_graph` and exactly why the manifest is reviewed rather than derived.

### 1.5 The recall corpus — settled

> **Recall corpus = `memory` + `wiki_page` + ADR pages.** All three carry a true `project_id` plus
> the optional `global` tag. **Everything else in the ledger is tool-only and NEVER enters
> recall**: `task`, `agent_pattern`, `agent_discipline`, `project`, `client`, `config`. They may
> still have wiki pages as bodies; **those pages must not be recallable.**

This is ADR-0206's rule, restated as a corpus boundary: ledger entities are fetched **by key**, not
recalled; ADRs alone stay ambient. **ADRs may carry the `global` tag** — a decision about
variable-naming conventions reaches every project.

Two things follow, and both are cars: the `page_type` exclusion moves into the query (C7), and
`task_list` pages stop being downweighted and start being excluded (C8).

**Decision G — the orphaned `global` rows.** They get **`local/aws-work`** as `project_id` **plus
the `global` tag**. `local/` is the correct form: verified that `/home/max/aws-work` has **no git
remote**. Owner and reach recorded separately, which is the whole point of §1.4.
The `memory`-side `"global"` (350) and `"system"` (604) rows are the same *question* with a
different answer per class — C6 decides each on the manifest, and the plan does **not** pretend
one sentence covers 1,034 rows.

## 2. The train

Twenty cars, one branch. Ordered so **step N does not break step N−1's tests**, and so the
correctness-bearing edits land before the mechanical ones.

```
C0  unblockers            ─┐ independent, land first
C1  gates                 ─┘

C2  host-side mint + transport      ← the only place identity is derived
C3  `project` param surface + enqueue-time stamping   (additive; `directory` still accepted)
C4  sessionless writers get explicit values
C5  FAIL-LOUD FLIP: fallbacks + tiers deleted        ← nothing can silently default after this
C6  registry rows + guard wired + backfill admin op  (code; execution gated to §8/runbook)
C7  ONE WHERE clause: project_id + `global` tag + page_type exclusion
                                                     ← ships WITH the backfill; §5.C6 sets
                                                       the post-boot pre-use deploy sequence
C8  superseded ADRs excluded in the SAME stage-1 WHERE + task_list → exclude
                                                     (+ delete the downweight machinery)

C9a  sweep — `_shared`
C9b  sweep — `backend`
C10  sweep — `core/**` + benchmarks + the judgement sites
C11  extra directory columns → migration 033
C12  branch residue → migration 032
C13a sweep — `tests/_shared`
C13b sweep — `tests/backend`
C13c sweep — `tests/core`
C13d sweep — `tests/e2e` + `tests/scripts` + weakening-allowlist governance
C14  docs / contracts / sdk-js / hook templates / seeded prose / dead hooks
C15a `002` schema edits + the four small fixes
C15  residue lint                                    ← lands last so it is green on arrival
C16  rehearsal + runbook + plan lifecycle
```

**Why this order.** C2 before everything so a **correct** value exists to sweep onto — the task
statement's constraint, honoured. C5 (fail-loud) immediately after C3/C4 have given every live
caller an explicit value, so the flip surfaces *forgotten* callers rather than *unconverted* ones;
flipping before C3 would red the whole repo, flipping after C9/C10 would let the sweep bake in a
silent `local/…`. C6 before C7 because a read path filtered on `project_id` over an un-backfilled
corpus returns nothing. C15 last because a residue lint written first is red for the whole train.

**Two intra-train dependencies a builder will otherwise trip over.** (1) #17's slug cap +
hash suffix changes `reslug.py:_project_id_to_slug`, and **C10(d) makes `adr_seed` a caller of
that function** — so #17 lands in **C6** (where the registry's key construction already lives),
not in the small-fixes car, and C10(d) is written against the post-cap signature. (2) C15a's `002`
edits are what §8's rehearsal steps 2 and 7 exercise, so C15a must precede C16 — which is why the
schema work is split out of C16 rather than left inside the car that tests it.

### C7 — one WHERE clause: `project_id` + the `global` tag + the `page_type` exclusion

**The architectural change of the train.** Filtering moves to **stage 1, in the query**. The
project predicate and the `page_type` exclusion are **ONE edit to ONE WHERE clause** and are not
split into separate cars.

**What is wrong today.** Both provider entry points are **scope-less** — verified by reading the
signatures: `Retriever.recall(query, max_results, min_heat, profile, deadline)`
(`backend/retrieval/core.py:517`) and `WikiStore.query(query, tags, category, max_results,
include_tag, exclude_tags)` (`_shared/wiki/store.py:945`). So `WikiStore.query()` searches the
**whole corpus**, and `WikiProvider.candidates()` then applies **two Python post-filters** —
`is_directory_eligible` at `providers/wiki.py:88` and `is_recall_visible` at `:100`.

**Consequence, in one sentence:** the top-N can be entirely out of scope and the caller gets
**zero results** — the limit is spent *before* filtering.

**Selectivity — the two halves of the predicate earn their place very differently, and the plan
says so rather than claiming both are wins:**

| half | keeps / removes | measured | verdict |
|---|---|---|---|
| `page_type` exclusion | removes a **minority** | agent-library + TOC + `task_list` pages are a small share of 2,343 | **rides along for free.** Over-fetch-and-drop would be nearly equivalent. Worth doing because it is the same edit — not because it is the win. |
| `project_id` (+ `global` tag) | **keeps** a minority | `yadgar` = **358 of 2,343 = 15.3%**; `aws-work` = **1,524 = 65.0%** (live `db_inspect`, 2026-08-10) | **this is the half that earns it.** A post-filter discards ~85% of everything it fetched for a yadgar-scoped recall. |

**The exclusion list is DERIVED from `POLICY_BY_TYPE`, never duplicated.** A disposition flip in
`policy.py` must change the emitted SQL automatically. Two lists = drift, and drift here is
invisible (the query silently keeps returning pages the policy says are excluded).

**Precedent exists in this exact store.** `_collect_scores_dispatch` (`_shared/wiki/store.py:897-907`)
already has a real SQL pre-filter path: `search_wiki_vectors_tagged`
(`_shared/storage/wiki.py:672-691`) runs
`SELECT id, vector::similarity::cosine(embedding, $qv) AS sim FROM wiki_page WHERE tags CONTAINS
$tag AND embedding IS NOT NONE ORDER BY sim DESC LIMIT $lim` — its own docstring says it
*"skips HNSW and FTS entirely — vector-only brute-force over pages tagged with include_tag (avoids
corpus dilution)"*. Same shape, different predicate.

> **The precedent is evidence of a CORRECTNESS problem, not a performance one. The earlier draft of
> this plan read it as "weak evidence the combination is not free" — that was wrong, and the
> correction changes the design.**
>
> Production vector search **is** the HNSW KNN operator:
> `SELECT id, vector::similarity::cosine(embedding, $qv) AS sim FROM wiki_page WHERE embedding
> <|{fetch_k}, 40|> $qv ORDER BY sim DESC` with `fetch_k = min(top_k * 4, 4096)`
> (`_shared/storage/wiki.py:650-661`); the memory side is identical
> (`_shared/storage/vector.py:52-63`). The KNN operator **selects its `fetch_k` neighbours first**,
> so an added `AND project_id = $p` filters *what KNN already chose* — top-K-then-filter, inside
> SQL. For a 15%-share project that is exactly the **dilution** the tagged path was built to escape:
> `search_wiki_vectors_tagged`'s docstring says *"Tag-scoped brute-force vector search… No HNSW —
> avoids dilution"* (`_shared/storage/wiki.py:672-691`). **Dilution here is a correctness failure —
> too few in-scope rows survive — not a latency one.**

**DECISION — the vector arm uses (a) brute-force cosine + `WHERE`, the in-tree precedent shape.**
Stated up front rather than left to a measurement, because the two candidate shapes have different
*correctness* properties, not just different speeds:

| option | verdict |
|---|---|
| **(a) brute-force cosine + WHERE** — the `search_wiki_vectors_tagged` shape | **CHOSEN.** Exact by construction: the filter runs before ranking, so a scoped recall cannot be starved. At this corpus (2,343 wiki pages, 3,006 memories) a full scan is a few thousand cosine ops — and a *project-scoped* scan is ~358 rows for yadgar. |
| (b) massively over-fetch K, then filter | Rejected as the primary shape: it makes correctness a function of a fudge factor, and the required over-fetch scales with how small the caller's project is (~6.5× for a 15% share, worse for a 1% one). |

**Scale ceiling, stated so the decision is falsifiable:** (a) is right *at this corpus size*. If a
single project's row count grows past the point where a brute-force scan misses the latency budget,
the answer is a **genuinely filtered ANN index**, not a return to top-K-then-filter. Record the
measured scan cost in the train doc so the next reader knows where the ceiling was.

**The FTS arm is unaffected — say so explicitly so nobody re-litigates it.**
`search_wiki_fts_scored` (`_shared/storage/wiki.py:633-644`) is
`SELECT id, search::score(1) AS score FROM wiki_page WHERE content @1@ $q ORDER BY score DESC
LIMIT $lim` — the `LIMIT` is applied **after** the predicate, so an added `AND` composes correctly
with no dilution.

**Scope.**

1. **Add a scope parameter to both entry points** and push it into the WHERE clause:
   `project_id = :current OR 'global' IN tags`, **plus** the derived `page_type NOT IN (…)`.
2. **Build the memory-side reach predicate.** `'global' IN tags` is inert for memories today —
   `recall_pipeline.py:424` never passes tags to `MemoryProvider` (only `:439`'s `WikiProvider`
   gets them). This is **new code**, not a rewiring.

### C8 — superseded ADRs excluded in the STAGE-1 WHERE, `task_list` excluded, downweight machinery deleted

**Redesigned 2026-08-10 by user decision. Two earlier designs are dead — recorded so neither is
re-proposed:** (i) a `POLICY_BY_TYPE` entry for `adr_superseded` plus a per-policy factor (mine —
killed by the shared-global-factor measurement and the sign inversion); (ii) removal at **pool
assembly** via a batched cross-engine lookup (also mine — killed by the reasoning below).

The user's instruction, verbatim:

> "we dont remove superseeded adrs i said we keep them but in the stage 1, we exclude them (and/or)
> in surrealdb query use where clause (using the policy) to not include them in results for much
> faster results."

and, on the tempting shortcut of reading the existing `adr-status:superseded` wiki tag:

> "the adr context is surrealdb will not have anything about their status"

**1. Status stays SOLELY in SQL.** `002_ledger_tables.py:153` `adr.status`, indexed at `:162`
`ix_adr_status`. One writer — ADR-0206-correct, unchanged from the previous design.

> **SurrealDB carries NOTHING about ADR status.** Do **not** reach for the `adr-status:*` wiki tag
> that exists on pages today: it is exactly the second writer ADR-0206 rejects, and the spine
> retires it. Any plan text, test, or builder instinct that reads status from SurrealDB is wrong.

**2. Load the superseded set ONCE, before the query, in the async route.**
`async def recall_route` (`backend/embed_service/embed_service_routes.py:124`) loads the superseded
slug/id set **before** `await asyncio.to_thread(_run_pipeline)` at `:208`, and passes it into the
pipeline as **plain data**.

**3. Inject it into the stage-1 WHERE as a bind param — in the SAME builder C7 constructs:**

```
… AND slug NOT IN $superseded_slugs
```

The set is tiny — **14 superseded ADRs in yadgar**, order tens across all projects — and is
cacheable by ledger version. Worst case one small SQL read per recall; **not** a lookup keyed by
returned candidates.

**Why this is strictly better than the pool-assembly design it replaces — the reasoning belongs in
the doc, not just in the decision:**

1. **Superseded ADRs never consume a `pool_limit` slot, because they are never fetched.** The
   pool-assembly design filtered *after* the providers returned — which is **the exact defect C7
   exists to delete**. C7's own thesis is *"the limit is spent before filtering"*; a C8 that
   re-adds a post-filter contradicts the car immediately preceding it.
2. **No `asyncio.run` inside a worker thread.** `_fanout_recall` is **sync** (`recall_pipeline.py:446`)
   and is reached via `to_thread`; MariaDB is **asyncmy, async-only** (`sql/mariadb.py:73`). A
   lookup placed inside `_fanout_recall` would need a **private event loop per recall** — the
   pool-churn trap this repo already warns about at `backend/admin_exec/invariants.py:892` and
   `backend/embed_service/embed_service_lifecycle.py:289`. Loading in the async route sidesteps it
   entirely rather than managing it.
3. **Exclusion stays policy-expressed and emitted by ONE WHERE builder shared with C7.** One place
   decides what is excluded.

> **Recorded so a future revision cannot silently reintroduce it (audit MF3, resolved-by-design):**

### ⚠ TWO shipped ADRs are contradicted — flagged, not smuggled

**ADR-0227's mechanism clause.** Verbatim: *"superseded ADRs are downweighted so severely they
cannot surface in the fusion pool, **implemented as a `POLICY_BY_TYPE` entry for `adr_superseded`**
rather than as exclusion, so they remain fetchable by key."* C8 does the opposite on both halves:
superseded ADRs are **excluded in the stage-1 WHERE** (not downweighted), keyed off the **SQL
`adr.status` flag** (not a `POLICY_BY_TYPE` entry, not a `page_type` retype). The retype is
denormalisation with two writers — ADR-0206 rejects it — and the downweight half is
**unimplementable as specified** (one global factor; multiply inverts on negative CE scores).

**ADR-0206's decision text — the bigger one.** *"Superseded ADRs are DOWN-WEIGHTED, never
excluded."* ADR-0206 rejects whole-document exclusion **by name**, with a live counterexample:
**ADR-0196 is superseded by ADR-0197, but its BACKUP half still binds** — *"superseded is not the
same as wrong."* Its only sanctioned escape hatch is **"exclusion-with-opt-in"**.

> **Required: ADR-0228 must amend BOTH ADR-0227 and ADR-0206**, and must address **partial
> supersession explicitly** — the ADR-0196 case, where a superseded ADR whose surviving half still
> binds becomes **recall-invisible and key-fetchable only**. **The user has accepted that
> consequence.** This plan does not proceed on the assumption that a mechanism swap inside an
> accepted ADR is a plan-level call. It is not.

**Recommended, and it costs nothing: ride the opt-in arm.** MF4 already forces the same WHERE
builder to carry an opt-in arm for `agent-prompt` and `rollup` (C7 item 5). **Superseded ADRs can
use that identical mechanism at zero extra cost** — excluded by default, returned when a caller
explicitly opts in. That makes ADR-0228 **narrow** ADR-0206's rule to its stated escape hatch
(*"exclusion-with-opt-in"*) rather than **overturn** its ADR-0196 counterexample, and it preserves
the "have we already decided this" lookup that is the whole reason superseded ADRs are kept. The
user is fine either way; this plan **recommends the opt-in arm**.

**Two claims from earlier drafts of this plan are struck as false:**
- ~~"Beyond that one clause, no fix in this plan reverses a shipped ADR."~~ — **false**: two are
  contradicted, and the ADR-0206 one is a decision, not a mechanism.
- ~~C8's mechanism "is exactly the mechanism ADR-0206 asked for."~~ — **false and
  cherry-picked**: it quoted ADR-0206's batched-lookup *implementation note* while **inverting the
  decision that note served**. The batched lookup is gone from the design anyway (Part 1).

a daemon-side session registry (contradicts ADR-0227's "never inferred" — §1.3 T1) and
bind-mounting host project directories into the DB-owning container (contradicts ADR-0227's
rejected-alternatives clause and `docs/saas/`'s isolation tiers, commit `5627a0d0`). If either is
later preferred, it needs a **superseding ADR** — flagged, not assumed.
