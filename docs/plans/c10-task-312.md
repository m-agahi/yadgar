# C10 — task 312: wiki near-duplicate gate passes EVERYTHING when the embedder fails

## State going in

Task 312 in the ledger: `wiki near-duplicate gate passes EVERYTHING when the
embedder fails: store.py:1272 find_similar_wiki_pages catches at logger.debug
and returns [] which reads as 'no similar pages'`.

The bug is in the **silent-degradation** family: a degraded dependency
(embedder cold start, model unload, transient embed-service outage) is caught
and downgraded to an empty success signal, lifting a guard that exists
specifically to block writes during that exact scenario.

## What the bug actually is

`WikiStore.find_similar_wiki_pages` (yadgar/_shared/wiki/store.py:1273-1278,
pre-fix) wraps the embedder call in:

```python
try:
    query_embedding = self._embeddings.encode_query(...)
except Exception as exc:                   # noqa: BLE001
    logger.debug("find_similar: encoder failed: %s", exc)
    return []
```

The drainer's similarity gate (`QueueDrainer._similarity_gate_for_drainer`,
yadgar/backend/queue_drainer/dlq.py:374, pre-fix) calls `find_similar_wiki_pages`
and treats the empty list as **"no similar pages — pass"**:

```python
candidates = _st._wiki.find_similar_wiki_pages(...)
...
if not candidates:
    return None            # gate passed → write proceeds
```

The embedder's absence was conflated with the embedder's verdict. A duplicate
landing during a cold start was indistinguishable from a clean write with no
duplicates. The DLQ sidecar logged `last_error: ""` for the original gate
failure because no exception was raised at this seam.

## What the fix is

The fix splits the empty list into two semantically distinct signals:

1. **`[]`** — embedder ran cleanly, no candidates above threshold → legitimate
   "no similar pages", gate passes.
2. **embedder unavailable** — encode failed or returned no embedding → gate
   CANNOT evaluate. For writes, this is fail-CLOSED: reject with a distinct
   reason so the DLQ sidecar names the real cause. For reads, this is
   fail-OPEN: a query that can't get an embedding should still return a
   useful answer.

The two-half split keeps the user-facing behaviour of `wiki_check_duplicate`
intact (degraded embedder → empty candidates, not a stack trace) while making
the WRITE path strict.

### Half 1 — `find_similar_wiki_pages` raises on embedder failure

`WikiSimilarityGateUnavailable` (new exception) is raised when the embedder
raises OR returns `None`. The empty list now means ONLY "embedder ran cleanly,
no candidates above threshold" — a strictly narrower contract. This is the
single source of truth: any caller (write-path, read-path) can branch on
type.

### Half 2 — Drainer (write path) catches the exception and rejects

`_similarity_gate_for_drainer` (dlq.py:413) wraps the `find_similar_wiki_pages`
call in `try/except WikiSimilarityGateUnavailable` and returns a rejection
dict with `reason="gate_unavailable"`. The hint surfaces the embedder outage
and points the operator at the `force=True` bypass as the deliberate override.
A new metric label `yadgar_wiki_add_rejected_total{reason="gate_unavailable"}`
counts these so they show up in dashboards distinct from `duplicate_detected`.

### Read-side stays fail-open

`wiki_check_duplicate` (yadgar/core/server/tools/wiki.py) and
`_autolink_filter_by_similarity` (yadgar/_shared/wiki/store.py) catch the
exception and convert to `[]`. A query that can't evaluate still helps the
user (no false "this is a duplicate" warning), and the gate's fail-closed
contract only applies to writes.

## What this car is NOT

- Not a fix to embedder availability itself. The detection is the gate's
  job; recovery is the embedder's.
- Not a change to the read-path fail-open semantics. A query returning
  "I can't tell, but I won't crash" is the right UX.
- Not a fix to the `force=True` bypass semantics — operators who want to
  land a write during a known embedder outage still can.
- Not a metric or dashboard change beyond the new label. Existing
  `yadgar_wiki_add_rejected_total` counter is extended, not replaced.

## Follow-ups (out of scope)

- A future car could add a `gate_unavailable` page to the maintenance envelope
  so operators see embedder outages in the same surface as DLQ rejections.
- The autolink filter's fail-open path could be tightened to log a warning
  (currently silent), but that's observability scope, not correctness scope.
