## Goal

Make the systemd-user unit set declared by `flake.nix` (in `/home/max/git/nix`)
match the canonical nine-unit set the Python renderer ships, AND add
`yadgar.target` so activation topology is identical across all three renderers

## Risks

- **Cycle in target → service → target.** `yadgar.target` `Wants=` the two
  daemon services; the services' `Install.WantedBy=` `yadgar.target`. systemd
  allows this (the target is the activator, not a runtime dependency; the
  services' `After=` stays empty w.r.t. the target). Empirically the Python
  renderer already runs this loop with no infinite-restart class.
  (`yadgar/tests/scripts/snapshots/systemd/podman/yadgar.target` is the
  reference shape; check the `Wants=` lines exactly.)
- **Activation-order regression on hosts that previously `enable`d
  `default.target` → both daemons.** systemd graph: target Wants services,
  services have no `After=target.target`. On first switch the daemons may
  start before the target "arrives"; this is fine (target is just a Wants
  aggregator) but worth a smoke-test on a non-production host first.
- **The FIFTH renderer (`modules/home/yadgar.nix`).** Living in the
  `m-agahi/nix` repo and not under test in the yadgar suite. The parity test
  added in step 4 covers it conditionally — `xfail` if the path is absent on
  CI. A future car should consider promoting it to an installed package, but
  scope here is parity-only.
- **yanked-from-old-system.** Hosts running with
  `default.target` symlinks will leave dangling symlinks after the flip.
  `git mv` semantics don't apply (nix is hash-addressed); a one-time
  `systemctl --user disable yadgar.service yadgar-backend.service`
  `&& systemctl --user enable --now yadgar.target` is needed. Document in
  the MIGRATION_NOTES.md handoff — NOT in this plan.
