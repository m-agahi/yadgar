## What the bugs were

**321** — `yadgar-subagent-stop.py` was a SubagentStop hook script. ADR-0156
retired it (the SubagentStop event is no longer needed — the cleanup that used
to run there moved to a different lifecycle point). The installer removed the
script. But nix-managed `~/.claude/settings.json` files still list the
SubagentStop hook with a path to the now-deleted script. The hook entry
"looks registered" — `settings.json` carries it — but is wired to a file that
does not exist on disk, so it is dead weight that the user sees as
`verify-hooks` flagging the entry as "unexpected" (a hook yadgar no longer
manages).

**322** — `verify-hooks` walks `~/.claude/settings.json`, checks every entry's
script path resolves to a real file, and that every "yadgar-managed" event has
an installer-managed hook. It does **not** exec the script, does not check
that the interpreter at the shebang still exists, and does not verify the
script's own imports resolve. A `["SubagentStop", "/usr/bin/python3
/path/to/deleted.py"]` entry passes `verify-hooks` if `/usr/bin/python3`
exists — even though the script is gone.

## Why no code change is needed for either

**321** — `test_yadgar_named_entry_yadgar_no_longer_installs_is_surfaced`
(yadgar/tests/hooks/test_verify_managed_hooks.py:259-264) explicitly asserts
that `verify_managed_hooks` flags a `subagent-stop` entry as `unexpected` when
the settings file lists it but the installer no longer ships it. This pins the
"yadgar reports the wiring is stale" half of the bug — the user sees the
warning. The fix for the OTHER half — making nix stop re-adding the entry — is
not a yadgar-side problem; it lives in `yadgar.nix` and is task 305.

`test_unexpected_alone_does_not_fail_the_check` (lines 266-277) pins the
companion contract: a foreign-installed unexpected hook surfaces as a warning
but does NOT make the whole check fail. This protects users who hand-edited
their settings.json from being yelled at.

**322** — `test_doctor_probes_managed_hook_wiring` (lines 288-297) asserts that
`scripts/install/yadgar-setup.sh` invokes `verify-hooks` from the doctor probe
path. `test_doctor_hook_probe_is_called_from_run_doctor` (lines 300-303)
asserts that `_probe_managed_hooks` is actually called from inside
`_run_doctor` (the doctor function body, not just the file). Together these
pin the contract that the "is it REGISTERED" check runs as part of the host
verification surface, so the user does have a hook-wiring doctor probe — even
if it is the limited REGISTERED check rather than a fully exec'ing WORKS
check.
