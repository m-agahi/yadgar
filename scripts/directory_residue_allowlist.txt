# ADR-0225 `directory` residue-sweep allowlist — produced by C10 (0047 §5).
#
# WHAT THIS IS
# ------------
# ADR-0225 retires `directory` as a scoping/identity concept and says the
# retirement is "enforced by a residue sweep rather than by review". C15 owns
# that lint. This file is the sweep's allowlist: every path here still contains
# a word-boundary `directory` AFTER C10, on purpose, with the reason recorded.
#
# Without this file C15 would be RED ON ARRIVAL against ~40 files that were
# never in any car and never should have been.
#
# THE RULE C10 APPLIED (from the plan, verbatim in intent)
# --------------------------------------------------------
# A file lands in this allowlist ONLY when EVERY `directory` in it is a real
# filesystem path (carve-out 3). One scoping use disqualifies the whole file.
#
# TWO KINDS OF ENTRY — read the tag, they are not the same claim
# --------------------------------------------------------------
#   carve-out-3  A genuine filesystem path. PERMANENT. Never sweep.
#   c11-blocked  A real scope key that CANNOT be renamed yet, because the
#                table beneath it has no `project_id` column. Migration 031
#                declared `project_id` on `wiki_page` and `memory` and NOWHERE
#                ELSE. Renaming the parameter while the SQL still reads
#                `WHERE directory_context = $dir` ships a caller-facing lie:
#                the caller passes `owner/repo`, the query matches zero rows,
#                and nothing raises. These are TEMPORARY — C11 adds the
#                columns, then they leave this file. They are also C11's
#                worklist.
#   c9c-blocked  Reaches `wiki_page`/`memory` (which DO have `project_id`) but
#                the READ is still keyed on `directory_context` in
#                `_shared/storage/{wiki,memory}.py`, which C9c is re-keying.
#                Rename after C9c lands, not before.
#
